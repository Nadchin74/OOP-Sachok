# Звіт про виконання: Ітерація 1 (Лабораторна робота №34)

**Проєкт:** CinemaSystem (Система управління кінотеатром)  
**Варіант:** 15

## 1. Мета ітерації
Запуск підсумкового міні-проєкту, визначення предметної області, створення архітектурного каркасу (на базі Clean Architecture) та реалізація першого вертикального зрізу — процесу бронювання квитків на сеанс.

## 2. Що вже працює (Реалізований функціонал)
- **Архітектурний каркас:** Solution розділено на логічні шари `Domain`, `Application`, `Infrastructure`, `Console` та `Tests` із налаштованими залежностями (Dependency Injection).
- **Предметна область (Domain):** Створено базові сутності `Movie`, `Showing`, `Booking`. Застосовано поліморфізм для квитків (абстрактний клас `Ticket` та його спадкоємці `StandardTicket`, `VipTicket` із різною логікою розрахунку ціни).
- **Бізнес-логіка (Application):** Реалізовано `BookingService`, який інкапсулює логіку вибору місць, перевірки їх доступності та формування замовлення.
- **Збереження даних (Infrastructure):** На даному етапі реалізовано In-Memory репозиторії (`InMemoryShowingRepository`, `InMemoryBookingRepository`) для ізоляції бізнес-логіки від бази даних.
- **Інтерфейс користувача (Console):** Створено консольне меню, що дозволяє користувачеві побачити сеанс, ввести своє ім'я, вибрати стандартні чи VIP місця та отримати підсумковий чек.
- **Тестування:** Написано юніт-тести за допомогою xUnit для перевірки інваріантів домену (негативні ціни, некоректні місця) та логіки розрахунку загальної вартості.

## 5. Ризики та обмеження поточної ітерації
- **Persistence:** Дані існують лише під час роботи програми. Після закриття консолі всі бронювання зникають (буде вирішено в Lab 35).
- **Concurrency:** Наразі не реалізовано механізм блокування місць, якщо кілька потоків/користувачів спробують одночасно забронювати те саме місце.
